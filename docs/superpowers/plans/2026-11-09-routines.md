# Routines Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Alexa-style routines: named, one-tap (or scheduled) sequences of "set these devices" and "wait" steps, personal or admin-shared, shown per room on the dashboard and built on a Routines page.

**Architecture:** The server owns everything that runs. A new `apps/server/src/routines/` module has pure step/schedule/access logic, a Prisma-backed store, an in-memory `RoutineRunner` (one run per routine, cancellable waits, parallel commands per step through `DeviceManager.setState`), and a minute-aligned `RoutineScheduler`. GraphQL exposes CRUD, run/stop/try, and two subscriptions (`routineRunChanged`, `routinesChanged`). The web app adds `apps/web/src/routines/` (data hooks, a pure draft model, list and editor UI) and a routine row on the dashboard.

**Tech Stack:** TypeScript; server: Apollo Server 5, graphql-subscriptions, Prisma 7 on Postgres, vitest; web: React 19, MUI 9, Apollo Client 4 + codegen, @dnd-kit/sortable 10, framer-motion, vitest + Testing Library.

**Spec:** `docs/superpowers/specs/2026-11-09-routines-design.md`

## Global Constraints

- Waits: whole minutes, **1 to 720** (12 hours).
- At most **20 steps** per routine, **50 devices per Set step**, **10 schedule rows**.
- A device appears at most **once per Set step**.
- Names are **1–40 characters** after trimming. They are unique per owner for personal routines and unique among shared routines for shared ones.
- Light actions: `on` is `true` / `false` / absent ("leave as is"). Brightness is **1–100**. Use `color` (RGB 0–255) **or** `colorTempK` (**1000–10000**), never both. `on: false` drops every other field. An action must change at least one thing. Plugs and switches support `on` only, and it is required. Only `LIGHT` devices of brand `GOVEE` or `TUYA` support brightness, color or colorTempK. `CAMERA`/`UNKNOWN` devices and power-strip parents with adopted outlets cannot be used.
- Every routine has at least one Set step with at least one device.
- Schedules use the **server's local time zone**. The time is `"HH:MM"` (24 h), and days are integers **1 = Monday … 7 = Sunday**, non-empty.
- Run statuses: `RUNNING`, `OK`, `PARTIAL`, `FAILED`, `INTERRUPTED`, `STOPPED`. Problem reasons: `UNREACHABLE`, `NOT_READY`, `NO_ACCESS`, `REMOVED`.
- Project rule: small files and components, one concern each. Pure logic goes in `lib/` (web) or plain modules (server) with tests.
- Server tests need Postgres with `DATABASE_URL_TEST` pointing at `home_test`. Commands: `pnpm --filter @home/server test -- <file>`, `pnpm --filter @home/web test -- <file>`. Web codegen runs in `pretest`/`typecheck`.

## Review Focus

1. **Event-loop lag at a minute boundary.** A tick that lands late (07:00:59, then 07:02:01) must still fire 07:01 schedules exactly once. Tested in Task 7 (`fires each minute between ticks once`).
2. **A device's kind changed after the routine was saved** (light → plug) while its action still has brightness. The run sends only the fields the device supports now, and skips the device as `NOT_READY` if nothing is left. Tested in Task 5.
3. **Routine or owner deleted mid-run.** The run is cancelled. Writing its last run must not throw or leave an unhandled rejection. Tested in Task 6.
4. **The same routine triggered twice at once** (double-tap, or a tap during a scheduled start). Exactly one run survives, and the older run's late results never overwrite the newer run's status. Tested in Task 5 (`a stale run never publishes after being replaced`).
5. **Try it on a draft with a device the user can't access**, or one deleted meanwhile. It reports a problem (`NO_ACCESS`/`REMOVED`) instead of failing the mutation. Tested in Task 6.

### Task 5: Routine runner

**Files:**
- Create: `apps/server/src/routines/runner.ts`, `apps/server/src/routines/run-outcome.ts`, `apps/server/src/routines/cancellable-delay.ts`
- Test: `apps/server/test/routine-runner.test.ts`

**Interfaces:**
- Consumes: `RoutineStep`, `fitAction` (Task 2); `DeviceManager.setState` (errors carry `extensions.code` `DEVICE_UNREACHABLE` / `DEVICE_NOT_READY` / `NOT_FOUND`).
- Produces:
  ```ts
  export type Problem = { deviceId: string; deviceName: string; reason: "UNREACHABLE" | "NOT_READY" | "NO_ACCESS" | "REMOVED" };
  export type RunSnapshot = { status: RunStatus; startedAt: Date; endedAt: Date | null; problems: Problem[] };
  /** Who the run acts for: null = full access (shared routines, admins); otherwise checked per Set step. */
  export type RunAs = { userId: string } | null;
  export type RunnerDeps = {
    setState(deviceId: string, patch: StatePatch): Promise<void>;
    device(id: string): Promise<{ id: string; name: string; kind: DeviceKind; brand: Brand } | null>;
    canAccess(userId: string, deviceId: string): Promise<boolean>;
    delay(ms: number, signal: AbortSignal): Promise<void>; // rejects on abort
    now(): Date;
    onChange(key: string, run: RunSnapshot): void; // key = routine id or "try:<userId>"
  };
  export class RoutineRunner {
    constructor(deps: RunnerDeps);
    start(key: string, steps: RoutineStep[], runAs: RunAs): void; // replaces a live run with the same key (no STOPPED event for the old one)
    stop(key: string): boolean; // → onChange(STOPPED); false if nothing running
    isRunning(key: string): boolean;
    stopAll(): void; // shutdown: abort silently
  }
  export function outcome(actionCount: number, problems: Problem[]): "OK" | "PARTIAL" | "FAILED"; // run-outcome.ts; 0 problems → OK; problems === actions (and >0) → FAILED
  export function cancellableDelay(ms: number, signal: AbortSignal): Promise<void>; // real setTimeout, cleared on abort
  ```
- Behavior: `onChange(RUNNING)` fires at start. Each Set step issues every action **concurrently** (`Promise.allSettled`). Per action: device missing → `REMOVED`; `runAs` set and the user lacks access → `NO_ACCESS`; `fitAction` returns null → `NOT_READY`. Error codes map to `UNREACHABLE` / `NOT_READY` / `REMOVED`, and any other error becomes `UNREACHABLE`. At the end, `onChange` fires with the outcome. A replaced or stopped run never calls `onChange` again, which is enforced by a per-run token check after every await.
